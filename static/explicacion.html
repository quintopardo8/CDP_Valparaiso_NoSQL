2. Modelo de datos: de tablas a documentos

En Oracle un envío y sus intentos de entrega vivían en tablas separadas, unidas por una clave foránea. En MongoDB los datos que se leen juntos se guardan juntos.

Relacional (Oracle)

enviosintentos_entrega cuartelescarteroscdp

Cada consulta necesita JOIN y el trigger vigila el INSERT en otra tabla.

Documental (MongoDB)

envios {
  _id, cliente_id, cuartel_id, peso_gramos, estado,
intentos_entrega: [ { intento_nro, cartero_id, resultado, tiempo_minutos } ]
}

cuarteles {
  _id, tipo_reparto, nivel_dificultad, ubicacion (GeoJSON),
carteros_asignados: [ { cartero_id, nombre, tipo_movilidad } ]
}

4. Anatomía del pipeline de sobrecarga

  
Reemplaza al trigger de alertas. Cada etapa recibe los documentos de la anterior y los transforma, igual que una línea de montaje.

  

    
$match
Deja solo los envíos pendientes.
estado = PENDIENTE

    
$group
Suma el peso por cuartel.
_id = cuartel_id
peso_total_g = $sum

    
$match
Filtra los que pasan el límite legal.
peso_total_g > 25000

    
$lookup
Trae los datos del cuartel (como un JOIN).
from: cuarteles

    
$unwind
Convierte el resultado del lookup en un objeto.
info_cuartel

    
$match
Solo cuarteles activos que reparten a pie.
tipo_reparto = A_PIE

    
upsert
Guarda o actualiza la alerta del día.
update_one(..., upsert=True)
